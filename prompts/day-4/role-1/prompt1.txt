# THERMALX — DAY 4 TASK

## ROLE 1 — FRONTEND & UI DEVELOPER

## TASK: INDUSTRIAL FACILITY INFORMATION PANEL

You are working on **ThermalX**, a JavaScript-first MVP for detecting, analyzing, classifying, and visualizing satellite thermal hotspots.

I am **Role 1 — Frontend & UI Developer**.

Your job today is to implement the **Day 4 frontend task** from our development plan:

> Build the **Facility Information Panel** that displays nearby industrial facilities associated with the currently selected thermal hotspot.

The project must remain simple and compatible with our existing architecture.

---

# 2. DAY 4 REQUIREMENT

The Day 4 objective is:

**Select a hotspot and see nearby industrial facilities, their distance, and their type.**

Role 1's specific responsibility:

**Create the facility information panel.**

The panel should work with industrial facility data supplied by the data/API layer.

Possible facility categories include:

* Factory
* Industrial area
* Power plant
* Refinery
* Mine
* Oil/gas infrastructure
* Other relevant industrial facility

The UI should make it easy to understand:

1. Which hotspot is selected
2. Which industrial facilities are nearby
3. What type each facility is
4. How far each facility is from the hotspot
5. Whether the facility is relevant as industrial context

# 6. SELECTED HOTSPOT BEHAVIOR

When the user selects a thermal hotspot:

1. Detect the selected hotspot.
2. Read the nearby industrial facilities associated with that hotspot.
3. Update the Facility Information Panel.
4. Remove stale facility information from the previous hotspot.
5. Show the currently selected hotspot's industrial context.
6. If there are no nearby facilities, clearly display:

"No nearby industrial facilities found."

Do not leave the previous hotspot's facility information visible.

---

# 7. FACILITY INFORMATION TO DISPLAY

For each facility, display as much of the available information as is safely supported by the data.

Preferred fields:

* Facility name
* Facility type/category
* Distance from selected hotspot
* Latitude
* Longitude
* OSM identifier, if available
* Relevant tags, if available

Do not invent facility names or information.

If a field is unavailable, hide it or show an appropriate fallback such as:

"Name unavailable"

Do NOT fabricate missing data.

---

# 8. DISTANCE DISPLAY

Distance should be displayed in a human-friendly format.

Examples:

* 850 m
* 1.2 km
* 3.7 km

If the data layer already calculates distance, use that value.

Do NOT implement a second competing distance-calculation system unless absolutely necessary.

The distance is contextual evidence only.

Use wording such as:

"Distance from hotspot"

Do NOT imply:

"Cause confirmed"

"Fire caused by facility"

"Illegal activity detected"

The ThermalX system is a decision-support system, not proof of causation.

---

# 9. INDUSTRIAL CONTEXT EXPLANATION

Add a small explanatory UI element explaining what this information means.

Example:

"Nearby industrial facilities are shown as contextual evidence. Proximity alone does not prove that a facility caused the thermal event."

This is important because the Day 4 plan explicitly treats industrial proximity as a **decision-support heuristic, not proof of attribution**.

Keep this explanation concise and visually secondary to the main information.

---

# 10. EMPTY / LOADING / ERROR STATES

The panel must handle all important UI states.

## Loading

Display something such as:

"Loading industrial context..."

Do not freeze the entire dashboard.

## No facilities

Display:

"No nearby industrial facilities found."

## Error

Display:

"Industrial facility data is currently unavailable."

Do not expose raw JavaScript errors to the user.

## Invalid data

Gracefully ignore malformed facility records.

The rest of the dashboard must continue working.

---

# 11. FACILITY CARD DESIGN

Create a reusable facility-card UI component.

Each card should visually separate:

* Facility name
* Facility type
* Distance
* Optional location/details

Example:

┌──────────────────────────────┐

│                              │

Use icons only if the existing UI already supports them or if a lightweight icon solution is already available.

Do not add unnecessary dependencies.

# 12. SORTING

If multiple nearby facilities are available, display them in a logical order.

Prefer nearest facilities first.

If the processing/data layer already supplies a distance value, sort using that value.

Do not perform duplicate spatial calculations in the UI.

# 17. VERY IMPORTANT — COMMENTS IN EVERY CODE SECTION

This is a mandatory requirement.

I want to understand this project easily later.

Therefore:

**ADD CLEAR COMMENTS TO EVERY MAJOR SECTION OF CODE.**

Comments must explain:

1. What the section does
2. Why it exists
3. What data it expects
4. What it returns/updates
5. How it connects to other modules when relevant

For example:

```javascript
// ------------------------------------------------------------
// FACILITY INFORMATION PANEL
// ------------------------------------------------------------
// This function updates the industrial-context section of the
// dashboard whenever a user selects a thermal hotspot.
//
// Input:
// - hotspot: currently selected thermal hotspot
// - facilities: nearby industrial facilities supplied by the
//   data-processing/API layer
//
// Output:
// - Updates the facility panel in the DOM.
// ------------------------------------------------------------
```

Use comments for major HTML sections too:

```html
<!-- =========================================================
     INDUSTRIAL CONTEXT PANEL
     Displays nearby industrial facilities for the selected
     thermal hotspot.
     ========================================================= -->
```

And CSS sections:

```css
/* ============================================================
   INDUSTRIAL FACILITY CARDS
   Styles the individual facility information cards shown
   inside the industrial context panel.
   ============================================================ */
```

Do NOT write meaningless comments such as:

```javascript
// Set x to 10
let x = 10;
```

Comments should explain the purpose and reasoning.

Do not comment every single line mechanically.

Instead, provide useful comments for every logical/major section so that another team member can understand the code months later.
